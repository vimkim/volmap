# Pinned CUBRID record-interpretation corpus

Complete 16,384-byte physical pages generated by CUBRID commit
`e1e651debf6cc100172bde96603b17424f9c135a` — the same engine that produced the
sibling [`e1e651de`](../e1e651de/README.md) corpus. All database content comes
from [`generate.sql`](generate.sql); there is no production or recovered data.

The sibling corpus pins allocation and page structure. This one pins the bytes
a **record interpretation** must decode, which the sibling corpus cannot
provide: it contains no class-object page, and its columns are deliberately
`BIT VARYING` to keep the string-compression path out of the way.

## What it covers

| Class | Class object | Rows | Why it is here |
|---|---|---|---|
| `interp_scalars` | `0\|195\|2` | `1\|641` | Every attribute type version one decodes; an all-bound row, an all-NULL row, and an LZ4-compressed inline VARCHAR |
| `interp_placeholders` | `0\|209\|3` | `1\|1025` | The types version one refuses to decode, which must render as typed placeholders |
| `interp_oos` | `0\|199\|1` | `1\|1153` | An inline value and a 16-byte out-of-row stub in the same column |
| `interp_altered` | `0\|207\|4` | `1\|1345` | Two representations of one class: `slot1` carries representation 1, `slot2` representation 2 |
| `interp_target` | `0\|210\|3` | `1\|769` | A referable (`DONT_REUSE_OID`) class, so it can be an OBJECT domain |
| `interp_reference` | `0\|195\|5` | `1\|897` | A bound and an unbound OBJECT column |

Incidental coverage worth knowing about, because it is hard to construct on
purpose:

- **System classes.** Page 195 also holds `dual` (slot 1), `_db_serial`
  (slot 3) and `_db_ha_apply_info` (slot 4). `_db_serial.current_val` is
  `NUMERIC(38)`, the widest NUMERIC domain the engine has.
- **All three variable-offset widths.** Records on these pages use 1-byte,
  2-byte, and 4-byte offset tables. Class records always use 4-byte.
- **Relocated class records.** The system class records on page 195 are
  `REC_NEWHOME`, reached by relocation from their own class OIDs, and slot 6 is
  one such `REC_RELOCATION`. A class-record reader must follow relocations
  rather than assume `REC_HOME`.
- **A bestspace page.** The second page of each heap carries a large slot 1
  that is a bestspace entry array, not a record. A record reader must not
  mistake it for one.

## Reproduction

Build and install the pinned engine, initialize its runtime environment, then
run — the database name must stay within CUBRID's 17-character log-prefix
limit:

```sh
mkdir -p "$CUBRID_DATABASES/db"
cubrid createdb --db-page-size=16K --db-volume-size=32M \
  --log-volume-size=20M volmap_records en_US.utf8 -F "$CUBRID_DATABASES/db"
csql -S -u dba -i fixtures/e1e651de-records/generate.sql volmap_records
```

Standalone `csql` exits after committing and flushing the snapshot. Extract a
page with a 16,384-byte block size and `skip=PAGE_ID`; volume 0 is the database
basename and volume 1 is its `_x001` extension.

A fresh run reproduces the class OIDs, page ids, and slot layout recorded in
[`manifest.toml`](manifest.toml) — that mapping is deterministic for this
schema. It does not reproduce the whole-volume digests, because `createdb`
stamps creation-time state into the volume headers. The per-page digests are
the integrity record for the pages committed here; verify them before replacing
any fixture.
