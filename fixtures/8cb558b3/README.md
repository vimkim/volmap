# Real develop disk corpus

These 19 physical pages were generated by the delivered CUBRID develop producer
`48a3e87e3d56d3b0c998d286f17fc6674bb5e547`, based on
`8cb558b3b264b5ed045ab24fa50b0ef825925349`, using the Debug installation recorded
in [manifest.json](manifest.json). All data is synthetic SQL from
[generate.sql](generate.sql). Standalone `createdb` and `csql -S` both exit before
any volume is read. No production data, observer page reads or native page tags
are used to manufacture these samples.

The manifest pins both complete source-volume hashes, page hashes, native
ordinals, generator inputs and commands. The complete 64/128 MiB source volumes
remain outside the repository. The generator scans native FILEIO_PAGE_RESERVED
identities and PAGE_TYPE ordinals independently of Volmap. It retains one page
per volume/family, separate heap header/chain examples, and all three overflow
pages. These are real storage structures written by the engine.

Coverage includes volume headers/bitmaps, file headers, heap headers/chains,
extensible hash envelope, catalog, B-tree roots, vacuum, dropped files and an
ordinary three-page overflow chain. It does not claim every possible page kind,
encryption format, record domain or all develop database layouts. In particular,
AREA, LOG and QUERY_RESULT are not present in this persistent dataset. The
canonical semantic wire corpus remains a separate v1.0/revision-2 artifact.

## Reproduce

Use a separate checkout/output directory for regeneration: `pages` and the
private database root must not exist. From the Volmap root, with the matching
pinned CUBRID installation:

```sh
python3 fixtures/8cb558b3/generate.py \
  --source /path/to/delivered-develop-source \
  --install /path/to/matching-debug-install \
  --database-root /path/to/new-private-database-directory
cargo +1.97.1 test --locked --test develop_fixture_corpus
```

The generator starts no service and touches only the new registry/database root
and its corpus output. It refuses another source commit. Clean shutdown makes
these immutable offline inputs. Fresh runs contain new creation timestamps and
identities; compare semantic results and provenance, and explicitly repin new
hashes rather than claiming that newly generated files must be byte-identical.

## Format authority and regression

Volmap explicitly selects the existing `develop` profile, whose source authority
is `cd593bc`. The [source-layout audit](../../.scratch/pgbuf-overlay-implementation/verification/07-develop-disk/source-layout-audit.json)
proves byte-identical definitions between that pin and `8cb558b3` for the six
central heap/file/envelope structures checked. GDB's type information from the
actual Debug library independently reports HEAP_HDR_STATS=1152 and FILE_HEADER=200.

The engine corpus exposed two decoder defects: treating the develop heap header
as the 1160-byte OOS layout, and rejecting file tables beginning at the develop
200-byte header boundary because the other profile requires 216. The latter
profile retains last-nth-page cache fields absent in develop. The heap's OOS
VFID also shifts subsequent statistics by eight bytes. The fix follows the
explicit profile; it never guesses from bytes or from wire page-kind names.

Six tests verify page hashes/types, volume/bitmap/file structure, heap header
statistics and chains, shifted catalog/B-tree/vacuum/drop semantics, the complete
overflow chain, and refusal under the wrong heap/file profile. Native boot heap
`0:129` has last page `0:130`, unfill 1634, one estimated data page, one record,
and 136 estimated record bytes. The corpus manifest and native layout logs
retain the source of those expectations. Existing `e1e651de` tests remain the
independent regression gate for `feat-oos`.
