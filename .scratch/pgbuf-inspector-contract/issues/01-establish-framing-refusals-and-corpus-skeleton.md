# 01: Establish framing rules, refusal frames and the corpus skeleton

**What to build:** A Volmap implementer can vendor a producer-owned corpus that already pins the wire framing rules and every refusal frame, verify its integrity with standard tooling, and see that the CUBRID canonical serializer reproduces each frame byte-for-byte in a unit test that demonstrably executed. This is the tracer bullet that establishes every layer at once: the implementation worktree and branch, the contract document, the canonical serializer module, the corpus layout with its checksum manifest, the Catch2 module, and the execution-evidence discipline.

**Blocked by:** None (can start immediately).

**Status:** complete

- [x] Work lands on a dedicated branch in a fresh worktree forked from the accepted format-aligned baseline `e1e651debf6cc100172bde96603b17424f9c135a`. The analysis worktree and all existing worktrees are untouched. No engine behavior, system parameter, socket, daemon or build option is added or changed.
- [x] The contract document exists in the producer-owned versioned contract directory assigned by the delivery plan. It cites the transport, gating, wire v1, security, verification, exact-LRU-membership and budget decisions as semantic authority and never restates them as new decisions. It specifies framing (one UTF-8 JSON object per line-feed-terminated frame, `type` as the first key, objects only, no raw line feed inside a frame), the canonical producer form (documented key order, no whitespace outside strings, base-10 integers without leading zeros or exponent, `true`/`false`/`null` literals, minimal escaping, ASCII-only producer strings), binary-byte limits including the line feed (4,096 for control and page frames, 65,536 for the handshake, nesting depth 16 counted from the frame object as depth 1, 64 MiB per scan, 65,536 visited slots and 65,536 pages), the absent-versus-null rule, and forward compatibility (unknown fields and unknown in-scan frame kinds ignored but counted against limits, unrecognized enum strings treated as unknown state, additive changes increment the minor, incompatible changes start a new major directory). It states that the canonical form binds the producer only and consumers accept any valid JSON within limits.
- [x] The contract specifies the `error` frame (`type`, `code`, `supported_majors` only with `version-unsupported`, `retry_after_ms` only with `rate-limited`), the five stable codes `version-unsupported`, `busy`, `incarnation-changed`, `identity-oversized` and `rate-limited` with each code's connection consequence, `parameter-off` as reserved and never emitted by a v1 producer, and that no error frame carries free text, OS error text, paths or process identities.
- [x] A producer-owned canonical serializer module exists. It defines a semantic error value made of plain scalars and enums, produces exact canonical bytes, enforces the control-frame limit at encode time and reports a would-exceed condition instead of emitting. It has no server-only or engine-internal dependency, adds no library, and compiles in every build mode so a unit test can build its source directly.
- [x] The corpus directory exists with one subdirectory per case holding the exact server-to-client bytes, a machine-readable expected outcome and, for generated cases, the semantic input. A README documents the case layout, the expected-outcome format with its outcome vocabulary (`accepted-complete`, `accepted-partial`, `discarded`, `refused`, `connection-closed`), the vendoring procedure for Volmap (copy verbatim, record aggregate hash and producer commit, recompute offline), and the change-control rule (any byte change increments the corpus revision and changes the aggregate hash, requiring matching offline evidence in both repositories before delivery).
- [x] Integrity artifacts exist: a checksum file in standard `sha256sum` format listing every corpus file except itself, sorted by path, and a JSON manifest recording contract version 1.0, corpus revision 1 and the aggregate hash defined as the SHA-256 of the checksum file's bytes. The manifest carries no commit identifier. `sha256sum -c` verifies the corpus on any Unix host with no project tooling.
- [x] Cases exist for each of the five refusal codes, each generated by the serializer from its semantic input, including `supported_majors` on `version-unsupported` and `retry_after_ms` on `rate-limited`. Each expected outcome is `refused`, names the code and states whether the connection closes.
- [x] A new Catch2 unit-test module is registered with its own option flag following the existing option-plus-subdirectory registration pattern and builds the serializer source directly into the test executable. Its cases prove byte-exact reproduction of every corpus stream from its semantic input, the canonical-form rules (key order, whitespace, integer and literal forms, escaping), would-exceed at 4,097 bytes with acceptance at 4,095 and 4,096, and corpus integrity by recomputing the checksum file and comparing the aggregate hash to the manifest.
- [x] Execution evidence is captured, not inferred: the test executable's own case listing and its summary line with nonzero case and assertion counts, recorded in this ticket's comments with the exact commit. Verification instructions in the contract and README use standard CMake option, build-target and executable terms. Personal task-runner recipes and workspace paths appear nowhere in committed text.
- [x] CUBRID conventions are preserved: Apache license headers, GNU indentation for C files and astyle for C++ files, include ordering with the memory wrapper last where required, `free_and_init` over bare `free`, header guards rather than `pragma once`. No indentation-only changes to existing files.
