# 02: Pin the handshake frames and the identity set

**What to build:** A Volmap implementer can decode a canonical `server_hello` carrying the complete permanent-volume identity set, LRU topology counts and the server incarnation, can emit a valid `client_hello`, and can exercise every handshake-time refusal, including identity overflow and a stale incarnation expectation, against pinned corpus bytes that the CUBRID serializer reproduces in executed tests.

**Blocked by:** 01 — Establish framing rules, refusal frames and the corpus skeleton.

**Status:** ready-for-agent

- [ ] The contract specifies `client_hello` (`type`; mandatory non-empty `supported_majors` of positive integers; optional `expected_incarnation`; optional ASCII `client` label of at most 64 bytes that is never interpreted) and `server_hello` (`type`; `protocol_major` 1; `protocol_minor` 0; `incarnation` as 32 lowercase hexadecimal characters holding 128 unpredictable bits generated once per server start; 64-bit `database_creation` as recorded identically in every volume header; `volumes` in ascending `volid` order, each with `volid`, 64-bit `volume_creation`, unsigned 64-bit `device` and `inode`; `shared_lru_count`; `private_lru_count`). Temporary volumes are excluded, the set is complete, and the producer never sends a subset.
- [ ] The contract specifies the exchange order: the peer is authenticated before any byte is read (stage-two work, stated here as a contract obligation); one hello and one reply; one outstanding scan request at a time; a protocol violation closes the connection without a frame; `identity-oversized` is emitted when the complete volume set cannot fit the handshake limit; `incarnation-changed` is emitted when `expected_incarnation` is present and differs from the server's incarnation. Consumers parse 64-bit integers exactly and never through floating point.
- [ ] The serializer gains semantic hello values and emits canonical `server_hello` bytes with volumes in ascending `volid` order, enforcing the 65,536-byte handshake limit with would-exceed reporting. It also emits the canonical `client_hello`, so the corpus's client frames are generated, not hand-written.
- [ ] Cases exist: a valid hello with at least two volumes together with the canonical client frames that elicited it (`accepted-complete`); a hello with additive unknown fields (accepted, ignored-field count recorded); a hello missing a mandatory field such as `volumes` (`discarded`, missing mandatory field); a hello exceeding the handshake limit derived by documented mutation (`discarded`, handshake too large); an `identity-oversized` refusal for a set that cannot fit; an `incarnation-changed` refusal following a client hello with a stale `expected_incarnation`.
- [ ] Tests prove byte-exact reproduction of each generated stream, handshake-limit behavior at 65,535, 65,536 and 65,537 bytes, ascending volume order in the output, exact rendering of maximal unsigned 64-bit device and inode values, and continued corpus integrity after the checksum file and manifest are regenerated with the corpus revision incremented.
- [ ] Execution evidence with named cases and nonzero counts is recorded in this ticket's comments with the exact commit. No engine behavior changes.
