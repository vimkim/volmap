# Set the TDE-encrypted page inspection boundary

## Question

What should version one do when the plaintext I/O-page envelope marks its 16,344-byte user region as AES- or ARIA-encrypted? Choose between an intentionally opaque metadata-only classification, optional decryption supplied through a narrowly defined key interface, or another bounded scope. Account for strict offline operation, no CUBRID runtime-library dependency, key custody and zeroization, remote web exposure, raw-byte policy, fixture availability, and the rule that ciphertext must never be parsed as page structures. Define the precise CLI/JSON/TUI/web behavior and whether decryption is a release blocker or future work.

## Answer

Version one supports optional offline decryption of permanent TDE user pages. Decryption is enabled only by the local process option `--tde-keys-file PATH`; there is no implicit `_keys` discovery and no key-content input through arguments, environment variables, stdin, JSON, or HTTP. Without that option, allocation/file metadata remains inspectable and AES/ARIA user pages are classified as `encrypted-opaque`. Supplying an invalid, unreadable, mismatched, or unusable key file is a fatal configuration error.

The implementation reads the key file once at startup, validates its pinned x86-64 layout, obtains `TDE_KEYINFO` through the boot-parameter HFID, validates and uses the selected master key to unwrap the permanent data key, then immediately zeroizes master-key and temporary buffers. Only the permanent data key remains in a non-debuggable, non-serializable, non-clonable secret container for the inspection lifetime and is zeroized on normal shutdown. A group/world-readable key file produces a prominent warning. No interface returns the key path, key identifiers or hashes, nonce, key material, ciphertext, application payload bytes, or decoded user values.

The canonical TDE inspection states are:

- `not-encrypted`: parse the page normally.
- `decrypted`: matching key material loaded; validate the plaintext structure before parsing it.
- `encrypted-opaque`: no key supplied; show only permitted plaintext identity, location, size, type/algorithm, allocation ownership, and the opaque classification.
- `key-error`: an explicitly supplied key file cannot be validated or cannot unwrap the database key; abort startup with a nonzero result.
- `decrypted-invalid`: key validation succeeded but decrypted structural invariants fail; classify the page as corrupt, never parse its ciphertext, and continue with partial results.
- `invalid-flags`: AES and ARIA bits are both present; classify the page as corrupt and never decrypt it.

CLI summaries count pages by TDE state and algorithm, and page detail shows only permitted structural/allocation metadata. Stable JSON represents the same state, page identity, location, size, algorithm, and diagnostics while omitting all forbidden fields. The TUI marks opaque pages with a lock/opaque treatment, decrypted pages with a `decrypted` badge, and corruption with diagnostics rather than byte dumps. The web server uses only key material loaded locally at startup, has no key endpoint, and exposes the same safe inspection model even when explicitly bound to `0.0.0.0`.

Record boundaries, slot/location, length, allocation state, record kind, and internal storage references required for page and OOS navigation are visible by default. Application payload bytes and decoded values are never visible in version one, for plaintext or decrypted pages; `--allow-raw-records` does not exist.

TDE support is a release gate. Approved synthetic, non-production fixtures generated from the pinned branch must cover AES-256-CTR and ARIA-256-CTR success, opaque mode, matching/mismatched and malformed key files, absent master-key index, failed decrypted structure, dual algorithm flags, and cross-interface non-disclosure. Ciphertext is never accepted as page-structure input under any failure mode.
