# Define validation oracles, fixtures, and acceptance gates

## Question

What evidence will prove the implementation conforms to the pinned `feat/oos` format and the agreed product behavior? Define source-derived layout assertions, generated normal and malformed fixtures, recovered-tool parity checks, golden human/JSON snapshots, property and fuzz boundaries, static-link verification, cross-distribution execution, large sparse-volume tests, snapshot-change tests, web/TUI interaction tests, and OOS cases covering `FILE_OOS`, `PAGE_OOS`, slotted OOS pages, chunk records, corrupt and multi-page value chains. State where the recovered program cannot be an oracle for new OOS behavior.

## Comments

### Standing human disposition

On 2026-08-19 the user directed every remaining ticket to accept the source-backed recommended option and continue without further HITL. The following oracle hierarchy and release gates are therefore accepted. Missing fixture evidence is a failed gate, not permission to weaken or mark a decoder complete.

### Oracle hierarchy

The accepted evidence order is strict:

1. pinned CUBRID source at `e1e651debf6cc100172bde96603b17424f9c135a` and an x86-64/GCC layout probe define byte contracts;
2. synthetic databases generated by that exact engine revision prove that supported layouts occur in valid files;
3. deterministic mutations of those captured fixtures prove containment and hostile-input behavior;
4. model/projection goldens prove the product contracts; and
5. an owner-authorized recovered executable may optionally corroborate only normalized legacy facts.

No lower oracle may override a higher one. Mutable local volumes, production data, comments, current `feat/oos` HEAD, the recovered UI/output text, and Volmap's own prior output are not format authorities. The current mutable `demodb` hashes do not match the recorded provenance and are explicitly excluded from acceptance.

### Implementation checkpoint

The first immutable generated slice now lives under `fixtures/e1e651de/`. Its manifest records the exact engine/CCI commits, build tools, source-volume geometry and hashes, clean standalone shutdown, 31 full-page hashes, and page/file roles. Tests validate every page hash and envelope identity, then directly decode volume/bitmap, tracker and file descriptors, heap header/chain, B-tree roots, E-hash slots, catalog, vacuum, dropped-file, a single-chunk OOS value, a three-chunk OOS value chain, and a two-page overflow chain. This closes the earlier absence of any pinned generated page corpus, but not the broader mutation/fuzz, layout-probe, TDE-generation, scale, cross-adapter, or distribution gates below.

## Answer

Version one is accepted only through the following layered corpus and gates.

### Pinned layout oracle

A small standalone C/C++ probe is compiled inside the pinned CUBRID worktree with the pinned build profile/compiler assumptions. It emits only integer `sizeof`, `alignof`, `offsetof`, enum, mask, and constant values for every supported persistent layout; it never links the CUBRID server or enters the Volmap build. The checked manifest includes compiler identity, target triple, endianness, CUBRID commit, source paths, macro/features, and probe-source hash. Rust tests assert every format constant and field range against the committed manifest, including:

- 16,384-byte I/O pages, the 16,344-byte user region, reserved/watermark fields, duplicate LSA, TDE flags/nonce, and every physical page ordinal;
- volume header offsets, enum values, variable-string bounds, sector-table geometry, and 64-page sectors;
- file header/descriptor, tracker, extensible-table, partial-sector, and file-type layouts;
- common slotted header/slot bit fields and the `REC_*` vocabulary;
- heap header/chain, MVCC/object-envelope variants, inline OOS reference, overflow headers, catalog-minimum, structural B-tree, E-hash bucket role, dropped-file, and vacuum layouts; and
- `FILE_OOS`, OOS header/data page roles, OOS page header, chunk header, link/flag masks, length arithmetic, and key-file/TDE structures.

The probe output is regenerated in verification and must be byte-identical. Any source, compiler, ABI, macro, or manifest drift creates a new format-profile review; tests never silently update expected numbers.

### Immutable generated fixtures

All accepted fixture bytes live under an immutable profile directory such as `fixtures/e1e651de/` with a machine-readable manifest. Every item records SHA-256, exact generation commands and SQL, engine/build identity, clean-shutdown state, volume purpose/order, intended page/file/slot identities, expected structural facts, and whether it is a whole volume or extracted page. Synthetic strings and values are conspicuously non-sensitive. Production databases and keys are forbidden.

The valid corpus contains at least:

- minimal primary and multi-volume stopped databases with volume headers, bitmaps, FTAB/tracker/allocation chains, heap header/data, minimal catalog, B-tree root/non-leaf/leaf/OID-overflow, E-hash bucket, recognized unknown/free pages, dropped-file, and vacuum-data coverage;
- sparse and fragmented allocation shapes, zero/one/many files, partial sectors, cross-volume file allocation, and conflicting claims created by a deterministic mutation rather than accepted as a valid engine output;
- heap HOME/NEWHOME/RELOCATION and a non-OOS BIGONE with complete multipage overflow where the pinned engine can generate them reproducibly;
- OOS-disabled and OOS-enabled databases proving `FILE_OOS`, OOS file descriptor/header, `PAGE_OOS` header/data roles, common slot geometry, heap inline references, and chunk records;
- single-chunk, exact inline/chunk boundary, exact page boundary, multiple values sharing one OOS page, multi-chunk same-page, multi-page, mixed-size, empty/null/non-OOS BIGONE, and multiple OOS files/volumes where supported; and
- AES-256-CTR and ARIA-256-CTR databases with synthetic key files for decrypted and encrypted-opaque behavior.

Opaque `QRESULT`, `AREA`, and unused volume `LOG` recognition may use synthetic envelope fixtures only; their bodies never become semantic goldens. Each semantic decoder remains incomplete until its valid fixture and manifest exist.

### Malformed and metamorphic corpus

A deterministic mutation tool applies one named mutation to a copied valid base and records base hash, exact byte range, before/after structural meaning without recording forbidden payload, and expected diagnostic/containment/coverage. Mutations cover truncation and short reads; negative, maximum, overflowing, nonmonotonic, overlapping, misaligned, and out-of-page offsets/counts/lengths; invalid/reserved/unknown ordinals; duplicate-LSA disagreement; dual TDE flags; wrong page/file/record roles; self-links, cycles, diamonds, duplicates, cross-file/cross-volume targets, early nulls, extra tails, count/length mismatches, and resource-budget stops.

For every containment level, tests assert both sides: dependent facts are absent or unresolved after the first failed boundary, while independently validated parents, siblings, and validated prefixes remain identical to the valid base. Metamorphic tests also assert that changing application payload bytes, key bytes, ciphertext, path/remark text, B-tree key bytes, catalog defaults, query tuples, or OOS fragments cannot change any permitted normalized fact except an explicit safe hash/fingerprint where defined—and cannot make those bytes appear in output.

### Unit, property, and fuzz boundaries

Checked-arithmetic and bounded-view unit tests cover every integer width, endian conversion, offset addition/multiplication, count-to-capacity proof, bit extraction, and typed identity conversion at `min`, `max`, just-inside, and just-outside values. Decoder tests consume owned bounded slices or internal `VolumeSource` reads and assert no unchecked indexing, disk-directed allocation, panic, undefined behavior, or guessed continuation.

Property tests generate structurally constrained valid and invalid envelopes, bitmaps, slot directories, link graphs, and resource policies. Core properties are deterministic results, permutation-independent claim reduction, idempotent enrichment for an existing target, monotonic immutable revisions, no cross-snapshot identity equality, coverage-ledger arithmetic consistency, cycle termination, and adapter-independent outcomes.

LibFuzzer targets every untrusted seam: discovery metadata, page envelope, volume header, bitmap, FTAB/extensible data, generic slots, heap/OOS/overflow/catalog/B-tree/vacuum detail, key-file parser/decrypt-then-validate, entity selectors/cursors, JSON request bodies, and HTML escaping. Seeds come only from approved synthetic fixtures. Each target has input/step/allocation/decode budgets and runs sanitizer jobs plus a long-running corpus job. Any crash, panic, timeout, excessive allocation, nondeterminism, forbidden-output sentinel, or parser progress without consuming a validated boundary is a failure. Fuzz tools and corpora are verification inputs, never runtime dependencies.

### Golden projections and non-disclosure

Canonical JSON is the primary product golden. Fixtures freeze schema version, deterministic entity order, typed identities, evidence locators, availability, coverage, diagnostics, outcomes, and explicit omission rules. JSONL goldens assert record framing/order and terminal summary. Human goldens disable ANSI, fix width/locale, and normalize only intentionally variable process facts; wording may evolve only with reviewed golden changes. HTML exports must be byte-identical for an equal build and revision and pass a parser check for one self-contained document, no remote URL/form/fetch, early CSP/referrer metadata, and no forbidden data.

Every adapter is fed unique sentinel sequences placed into synthetic application values, OOS/overflow fragments, B-tree keys, catalog defaults, query tuples, ciphertext, master/data keys, nonce, token, host paths, volume remarks, and source errors. Tests search CLI human/JSON/JSONL, TUI cells/copy mode, HTTP headers/bodies/errors, HTML, diagnostics, logs, panic text, and temporary spill. A sentinel occurrence is release-blocking. Structural byte ranges must end in `bytes_withheld` and never serialize the underlying slice.

### TUI and web interaction oracles

The TUI separates a pure state-transition/render model from Crossterm I/O. Table-driven tests cover 160×45, 120×36, 80×24, smaller unsupported terminals, resize preservation, ASCII fallback, focus visibility, every keyboard action, mouse equivalence, filters/search, overlays, cancellation, chain traversal, corruption, loading, invalidation, and terminal restoration after success/error/panic. Render assertions target named regions and semantic cells rather than brittle full ANSI streams; a small reviewed no-color screen snapshot catches layout regressions.

Web tests exercise the Axum router in process and a real headless browser against a loopback listener. They cover the Atlas hierarchy, virtual-sector cursors, all five scenarios, keyboard/focus behavior, responsive desktop/tablet/phone layouts, deep-enrichment revision transitions, stale revision/cursor handling, cancellation, diagnostic containment, and deterministic export. Security cases cover missing/wrong bearer tokens, query/fragment/storage token absence, duplicate/wrong Host, DNS-rebinding names, missing/null/mismatched Origin on POST, cross-site fetch metadata, wrong content type/method, body/URL/concurrency/rate limits, cache/CSP/frame/referrer/nosniff/CORP headers, traversal/encoding tricks, source invalidation, SIGINT/SIGTERM drain, and explicit `0.0.0.0` startup warnings. No CORS allow-origin header is emitted.

### Snapshot, scale, and resource tests

An instrumented `VolumeSource` deterministically changes size, file identity, timestamps, page LSA, or bytes between manifest, fast scan, query, and enrichment checks. Each mutation must atomically terminally invalidate the snapshot, cancel new deep work, preserve only diagnostic views of published revisions, reject enrichment, and require a new process/snapshot. Merely touching metadata while all required identity/fingerprint facts remain stable is tested according to the final fingerprint algorithm, not guessed.

Scale tests cover small dense, large dense, large sparse, allocation-fragmented, corruption-heavy, and OOS-heavy profiles. A real sparse-file case validates positional I/O, logical size handling, hole behavior, disk usage, and absence of mmap/SIGBUS hazards; an internal synthetic source drives very large trusted counts without allocating a real file. Assertions use Ticket 17's measured resource policy: admitted work stays within resident/spill/worker/decode ceilings, non-admitted work does not begin, cancellation latency is bounded, graph/query results remain deterministic across worker counts, and complexity follows the accepted page/claim formulas. No test relies on an untrusted on-disk count to size memory.

### Recovered behavioral parity

The recovered program is never a mandatory test dependency. If and only if separate written internal approval exists, a quarantined job may run it as a black box on the exact approved non-sensitive fixture hash and compare a narrow normalized intersection: discovered volumes, volume/sector geometry, legacy reservation/allocation totals, and pre-OOS page classifications whose meanings are independently sourced. It records tool hash, fixture hash, command, normalized facts, and disagreement without retaining or copying expressive output.

The recovered program is **not an oracle** for `FILE_OOS`, `PAGE_OOS`, slotted OOS pages, OOS chunk headers, heap OOS references, multi-page/value chains, new OOS allocation semantics, TDE behavior, evidence/coverage/diagnostic rules, any UI, or any security/export contract. It cannot establish correctness merely by agreeing, and disagreement never overrides pinned source or generated fixtures. Public release does not include recovered evidence without the separate owner/counsel gate.

### Distribution and release gates

The final candidate is built twice from the same reviewed source revision in different paths with the exact locked toolchain, dependency graph, and environment. Cargo may fetch dependencies during either build. The binaries must be byte-identical; `file` must report stripped x86-64 static PIE, `readelf -d` must contain no `NEEDED`, and `ldd` must report static/not-dynamic. The binary then executes the same fixture suite and canonical queries on supported x86-64 Linux families representative of glibc and musl users (at least Debian/Ubuntu, Rocky/RHEL-compatible, and Alpine) without installed Rust, CUBRID, glibc, installation assets, or third-party network services. Runtime networking may be disabled in this test to prove that self-containment; it is not a build constraint.

A release fails closed unless all of these are green: pinned layout regeneration; immutable fixture hashes; decoder/mutation/property/fuzz suites; OOS and TDE matrices; cross-adapter canonical parity and non-disclosure; TUI/web interaction and security suites; snapshot-change and resource/scale gates; locked duplicate builds; static ELF proof; cross-distribution execution; dependency/license/advisory policy; notices, SBOM, provenance, source and binary checksums; and the company public-release approval already required by Ticket 14. Unsupported detail may produce the agreed `success-limited` result, but a missing required fixture, parser, security test, or release artifact is not an accepted limitation.
